## 模块 00：项目脚手架（2026-08-29）

### E00-1 Docker 端口冲突：`ports are not available: bind: 0.0.0.0:3306`
- **现象**：`docker compose up -d` 后 MySQL 容器立刻退出，报 `Only one usage of each socket address`
- **原因**：宿主机 3306 已被本机原有的 Windows MySQL 服务（mysqld.exe）占用
- **排查**：
  ```bash
  netstat -ano | findstr 3306        # 找到 LISTENING 行末尾的 PID
  tasklist /FI "PID eq 6852"         # 确认进程身份
  ```
- **解决**：端口映射改为 `3307:3306`，JDBC URL 同步改为 `localhost:3307`；不动本机已有服务
- **预防**：启动容器前先 `netstat -ano | findstr <端口>`；记牢映射格式是"宿主机:容器"

### E00-2 `java -jar` 报"没有主清单属性"（no main manifest attribute）
- **现象**：jar 能打出来（仅几百 KB），运行即报错
- **原因**：自定义父工程（非 spring-boot-starter-parent）时，`spring-boot-maven-plugin` 的
  **repackage 目标不会自动执行**，打的是普通瘦 jar，缺 `Main-Class`
- **解决**：父 pom 的 pluginManagement 里给该插件显式加：
  ```xml
  <executions><execution><goals><goal>repackage</goal></goals></execution></executions>
  ```
- **验证**：fat-jar 应为几十 MB（依赖全打包在内）
- **教训**：**不用官方 parent 时，它默认替你做的事都要自己补**——这是自定义父工程第一坑

### E00-3 接口 500：`parameter name information not available via reflection`
- **现象**：`GET /users/1` 返回 500；日志提示 `Ensure that the compiler uses the '-parameters' flag`
- **原因**：`@PathVariable Long id` 未显式写名字时，Spring 6.1 需要反射读取方法参数名；
  编译器默认丢弃参数名信息（Spring Boot 3.2 / Framework 6.1 移除了旧的字节码兜底解析）
- **解决**：父 pom 加 `<maven.compiler.parameters>true</maven.compiler.parameters>`
- **预防**：或给注解显式写名字 `@PathVariable("id")`；两者都做最稳
- **典型场景**：老项目从 Boot 2.x 升 3.x 时大批接口突然 500，就是这个

### E00-4 Windows curl 发中文 JSON：`JSON parse error: Invalid UTF-8 start byte 0xbb`
- **现象**：含中文的 POST 请求 500，纯英文正常；服务端 Jackson 解析失败
- **原因**：Windows 控制台默认 **GBK** 编码，命令行参数里的中文以 GBK 字节发出，
  服务端按 UTF-8 解析（0xbb 正是"机"字 GBK 编码首字节）
- **解决**：中文请求体先存为 UTF-8 文件再发：
  ```bash
  printf '{"productName":"机械键盘"}' > order.json     # Git Bash 的 printf 输出 UTF-8
  curl -X POST ... -H "Content-Type: application/json; charset=utf-8" --data-binary @order.json
  ```
- **预防**：接口测试用 Postman/Apifox；或服务部署时统一 `-Dfile.encoding=UTF-8`

### E00-5 缺参数/请求体解析失败被兜底成 500（应为 400）
- **现象**：`GET /orders` 不带 `userId` 返回 `{"code":500,"message":"系统内部错误"}`
- **原因**：Spring 抛出的 `MissingServletRequestParameterException`、
  `HttpMessageNotReadableException` 落入兜底 `Exception` 处理器
- **解决**：`GlobalExceptionHandler` 为这两个异常单独加 `@ExceptionHandler` → 400 + 明确提示
- **经验**：**500 只留给未知异常**；可预见的客户端错误一律 4xx，这是排障判断"锅在前端还是后端"的关键信号

### E00-6（预防型）服务连不上数据库：`Communications link failure`
- **排查三连**：
  1. `docker ps` 看 micro-mysql 是否 `healthy`（不是 running 就够）
  2. JDBC URL 端口是 **3307**（映射后的），不是容器内部的 3306
  3. 密码与 docker-compose.yml 的 `MYSQL_ROOT_PASSWORD` 一致

### E00-7 git 提交报 `Unable to create '.git/index.lock': File exists`
- **现象**：`git add/commit` 直接失败，提示"Another git process seems to be running"
- **原因**：上一个 git 操作被中途取消/崩溃，留下了残留锁文件 `.git/index.lock`
- **解决**：确认没有 git 进程在跑（IDEA 等）后，删除锁文件：
  ```bash
  rm -f .git/index.lock
  ```
- **预防**：不要同时开多个终端对同一仓库做写操作；被杀掉的 git 命令要检查是否留锁

### E00-8 docker exec 查询中文显示 `????`（数据本身没坏）
- **现象**：`docker exec micro-mysql mysql -e "SELECT product_name FROM t_order"` 输出 `????`
- **原因**：非交互模式下 MySQL 客户端默认用 latin1 字符集收发数据，中文变问号。
  **注意数据是完好的**（用 GUI 客户端或加字符集参数即可看到原文），只是显示层乱码
- **解决**：命令行加参数 `--default-character-set=utf8mb4`：
  ```bash
  docker exec micro-mysql mysql -uroot -proot123 --default-character-set=utf8mb4 \
    -e "USE micro; SELECT * FROM t_order;"
  ```
- **鉴别口诀**：先判断"数据坏了"还是"显示坏了"——换一个客户端（Navicat/IDEA）看同一行，
  能显示就是显示问题；两端编码链路（服务端→客户端→终端）任一处不匹配都会乱

### E00-9 参数类型不匹配被兜底成 500（应为 400）—— 模块00考题现场教学
- **现象**：`GET /users/abc`（路径参数传字母给 `Long id`）返回 `{"code":500,"message":"系统内部错误"}`
- **原因**：Spring MVC 在**调用 Controller 之前**做参数绑定时抛
  `MethodArgumentTypeMismatchException`（请求根本没进 Controller/Service），
  该异常无专属 handler，被 `@ExceptionHandler(Exception.class)` 兜底成 500
- **机制**：Spring 选 handler 按**异常类的继承树最具体匹配**——
  `BusinessException` 精确命中专属 handler（1001）；无专属 handler 的异常才落到 `Exception` 兜底（500）
- **解决**：新增 `@ExceptionHandler(MethodArgumentTypeMismatchException.class)` → 400 + 参数名提示
- **验证技巧**：在 `UserService.getById` 打断点，请求 `/users/abc` 不停（没进 Service），
  请求 `/users/999` 才停——断点是"代码是否执行"的铁证
- **经验**：看到 500 先读堆栈第一行，判断异常"出生在哪一层"（绑定层/业务层/数据层）

## 模块 01：Nacos 注册中心

### E01-1（安全预警）Nacos 单机模式默认不开启鉴权，控制台"免密裸奔"
- **现象**：浏览器直接打开 localhost:8848/nacos，不登录就能看服务列表、增删配置；顶部横幅提示"当前集群没有开启鉴权"
- **原因**：standalone 模式默认 `nacos.core.auth.enabled=false`，nacos/nacos 账号形同虚设
- **风险**：任何能访问 8848 端口的人都可读配置（含密码）、删服务、改配置——公网部署=事故
- **正确姿势**：生产开启鉴权（容器环境变量 `NACOS_AUTH_ENABLE=true` + 自定义
  `NACOS_AUTH_TOKEN/NACOS_AUTH_IDENTITY_KEY/VALUE`，客户端 yml 配 username/password）+ 网络隔离（8848/9848 不对公网开放）
- **学习环境**：仅本机可接受，但要心里有数；2026-08-31 已向学员讲明

## 模块 03：OpenFeign 服务调用

### E03-1 启动失败：`No Feign Client for loadBalancing defined. Did you forget to include spring-cloud-starter-loadbalancer?`
- **现象**：加了 openfeign 依赖和 @EnableFeignClients，启动即失败；异常链末端是上面这句
- **原因**：Spring Cloud 2022+ 起，`spring-cloud-starter-openfeign` **不再传递依赖 loadbalancer**。
  Feign 接口按"服务名"调用（而非写死 URL）时，必须由 LoadBalancer 负责"从多个实例挑一个"，
  这个组件不在 classpath 就无法创建代理
- **解决**：order-service pom 显式加 `spring-cloud-starter-loadbalancer`（版本由 SC BOM 管理）
- **读堆栈技巧**：巨型启动异常是"甩锅链"，从最后一个 `Caused by` 往上读——最后一环才是根因；
  本例：orderController ← orderService ← UserClient(FactoryBean) ← No Feign Client for loadBalancing
- **另**：启动日志 `[Nacos Config] config[dataId=order-service.yml...] is empty` 是 optional 导入
  尚不存在的配置的正常提示，无害

## 模块 07：Zipkin 链路追踪

### E07-1 链路在 Feign 调用处"断裂"（下游出现新 TraceId）
- **现象**：Zipkin 里下单主链路只有 gateway+order 的 Span；user-service 的请求**单独成一条 Trace**（TraceId 不同但时间吻合）
- **原因**：`spring-cloud-starter-openfeign`（4.1.x）**不含 feign-micrometer**。缺它时 Feign 出站调用：
  ①不生成 Span；②请求头不带追踪上下文（traceparent/b3）→ 下游当新请求处理，链路断开
- **解决**：order-service 加依赖 `io.github.openfeign:feign-micrometer`（版本由 SC BOM 管理）
- **诊断方法**：对比两条 Trace 的 TraceId 与时间戳；或看主链路 Span 树里有没有"Feign 调用"子 Span
- **经验**：追踪是**分组件埋点**的——给应用加 micrometer-tracing 只覆盖 MVC/WebFlux/JDBC 等框架自动埋的，
  每个独立客户端库（Feign/OkHttp/Kafka 客户端…）要各自的埋点模块
