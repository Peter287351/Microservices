## 模块 00：项目脚手架

**Q1 父 pom 的 `<dependencyManagement>` 和子模块直接写 `<dependencies>` 有什么区别？为什么版本号集中在父 pom？**
参考答案：`dependencyManagement` 只**声明版本的"价目表"**，不真正引入依赖；子模块在 `<dependencies>` 里引用时**不用写版本号**，自动继承父 pom 锁定的版本。集中管理的原因：三个服务的公共依赖必须版本一致，否则"同一个类两个版本"会引发运行时 `NoSuchMethodError`；升级时只改父 pom 一处。我们工程中三个 BOM（Boot/Cloud/Alibaba）就是三张官方"兼容版本价目表"（[pom.xml](../pom.xml)）。

**Q2 t_order 已有自增主键 id，为什么还要唯一的 order_no？amount 为什么用 decimal(10,2)？**
参考答案：主键 id 是**数据库内部的物理标识**（InnoDB 聚簇索引，自增顺序写入性能好），对外暴露会泄露业务量；order_no 是**面向业务的单号**（可读、可换算法如雪花 ID），两者职责分离。amount 用 decimal 因为 double 是二进制浮点，无法精确表示 0.1（0.1+0.2=0.30000000000000004），钱不能算错；Java 侧对应 BigDecimal。详见[数据库设计说明](数据库设计说明.md)。

**Q3 两服务共用 micro 库，哪个说法正确？—— B**
参考答案：B 正确。真实微服务"一服务一库"，共库的本质是"分布式部署的单体"；拆库后跨服务数据一致性需要 Seata（模块 09）。模块 00 共库是学习阶段的简化。

## 模块 01：Nacos 注册中心

**Q1 实例列表为什么缓存在调用方本地？会调到挂掉的实例吗？**
参考答案：缓存为了①性能（不用每次调注册中心）②解耦（**Nacos 挂了也能照常调用**）。会：实例死亡到缓存更新有时间窗（心跳 15 秒标记不健康/30 秒剔除 + 推送传播），窗口内的调用会失败。真正兜底靠调用方的重试、多实例轮换、熔断（模块 04/06）。

**Q2 注册中心挂了会怎样？**
参考答案（含实验验证）：**已启动的老服务不受影响**——本地缓存照常用，调用正常；客户端后台无限重连，Nacos 恢复后自动重连并**重放注册**（日志：mark to redo → Redo instance operation REGISTER）。**新启动的服务**无法注册（反复报连接失败），但也能启动。所以注册中心设计上是"可被牺牲"的：本地缓存+重连+重放三件套。

**Q3 实例被 kill -9，Nacos 靠什么发现？—— B（心跳超时）**
参考答案：实例每 5 秒心跳，15 秒没心跳标记不健康、30 秒剔除。C"调用方报错反馈"不对：调用方报错≠实例死（网络抖动、超时、调用方自身 bug 都会报错，会误杀），健康判定的职责归实例自己的心跳——职责分离。调用方的对策是重试/换实例/熔断，不是举报。

## 模块 02：Nacos Config 配置中心

**Q1 optional: 前缀去掉会怎样？数据库配置该不该加？**
参考答案：去掉后 Nacos 里没有对应 Data ID 服务就**拒绝启动**（fail-fast）。取舍口诀：**核心配置 fail-fast（宁可起不来，不要半路死）——数据库配置不加 optional；锦上添花的配置（文案/开关）用 optional**。引导配置（连 Nacos 自己的地址）必须留在本地 yml。

**Q2 改了配置接口不生效，按概率的 3 个原因？**
参考答案：①类没加 `@RefreshScope`（90%）：`@Value` 只在 Bean 创建时注入一次，Environment 更新了 Bean 不知道；@RefreshScope 在收到刷新事件后**销毁 Bean、下次请求时用新值重建**。②改错 Data ID/Group/命名空间（注意 `.yml` 和 `.yaml` 是两个 Data ID）。③YAML 内容格式错（缩进/冒号空格），解析出的 key 对不上。

**Q3 数据库密码放本地还是 Nacos？绝对安全吗？**
参考答案：放 Nacos。理由：①改密码不用改代码重新打包（动态轮换，泄漏后几分钟换掉）；②git 仓库不再有明文密码（仓库泄露≠密码泄露），且有变更审计。本地只留连接 Nacos 的引导配置，远程配置优先级更高，本地可作应急兜底。**不绝对安全**：Nacos 本身要设防——我们学习环境就没开鉴权（[E01-1](错误知识库.md)），任何人都能读配置。安全=层层设防：鉴权+网络隔离+控制台强密码+必要时加密。

## 模块 03：OpenFeign 服务调用

**Q1 接口没有实现类，为什么能发 HTTP 请求？**
参考答案：**JDK 动态代理**。`@EnableFeignClients` 扫描 @FeignClient 接口，运行时生成代理对象（报错栈里的 `$Proxy134`、`FeignInvocationHandler.invoke` 就是它）。调用接口方法时代理拦截：读方法注解→拼 HTTP 请求→拿服务名查 Nacos→发请求→JSON 反序列化成返回值。声明式=只声明"调什么"，怎么调框架包办。

**Q2 停掉 user-service 后下单失败：快速失败还是卡死？现象叫什么？解法方向？**
参考答案：**快速失败**——LoadBalancer 发现实例列表为空（`No servers available`），根本不发网络请求直接抛 503。现象叫**级联失败**（调用方被拖下水）。解法方向：多实例+负载均衡（模块 04）、熔断降级返回兜底（模块 06）、重试、异步解耦（模块 08）。

**Q3 为什么要 UserDTO 而不共享实体类？**
参考答案：服务间只通过 **HTTP+JSON 契约**耦合。共享实体 jar = 编译期强耦合：对方改字段你编译就炸，版本同步是地狱；且实体是对方内部库表结构，暴露即失封装。每个服务用自己的 DTO（"本地影子"/防腐层），对方内部随便重构，契约不变你就无感。

## 模块 04：LoadBalancer 负载均衡

**Q1 Nginx 和 Spring Cloud LoadBalancer 的本质区别？内部调用为什么选后者？**
参考答案：本质区别是**谁来挑实例、实例列表从哪来**：Nginx 是独立中间人（服务端 LB），列表靠手工配置文件；LoadBalancer 在调用方**进程内**（客户端 LB），列表从注册中心（Nacos）自动获取。内部调用选后者：①无需手工维护 upstream（服务动态扩缩容，Nacos 自动感知）；②少一跳网络转发，点对点直连；③与 Feign/注册中心天然集成（`lb://` 协议）。Nginx 适合做**对外的统一入口**（模块 05 网关的前置）。

**Q2 停掉 8083 后 LB 怎么知道它死了？脏窗口多长？**
参考答案：机制链=实例停机时主动注销（优雅关闭）或心跳超时（强杀时，15 秒不健康/30 秒剔除）→ Nacos 更新实例列表 → **推送**给订阅方 → LoadBalancer 更新本地缓存。脏窗口约 **30 秒级**（心跳剔除时间+推送/缓存刷新延迟），窗口内调用可能打到已死实例——生产用"失败重试到下一个实例"兜底。

**Q3 想让性能强的实例多接客，什么算法？**
参考答案：**加权轮询/加权随机**。需要信息：①每个实例的权重值（手工配或按 CPU/内存自动估算）；②实时健康状态（挂了权重归零）。Nacos 控制台可给实例设权重，配合 Spring Cloud Alibaba 的 NacosLoadBalancer 生效（默认 RoundRobin 不读权重，需开启）。思路扩展：最少活跃调用（谁手头活少给谁）适合耗时差异大的场景。
