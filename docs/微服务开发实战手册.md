# 第一部分 · 工程骨架（模块 00，一切的地基）

## 1.1 Maven 多模块 + 父 pom 锁版本

**核心思想**：版本只在父 pom 写一次，子模块引依赖不写版本号——杜绝版本冲突。

```xml
<!-- pom.xml 关键段 -->
<dependencyManagement>
  <dependencies>
    <!-- 三张"版本价目表"：Boot 管 Spring 全家桶，Cloud/Alibaba 管微服务组件 -->
    <dependency> <!-- Boot 3.2.4 --> org.springframework.boot:spring-boot-dependencies (pom/import) </dependency>
    <dependency> <!-- SC 2023.0.1 --> org.springframework.cloud:spring-cloud-dependencies (pom/import) </dependency>
    <dependency> <!-- SCA 2023.0.1.0 --> com.alibaba.cloud:spring-cloud-alibaba-dependencies (pom/import) </dependency>
    <dependency> <!-- 内部模块 common 也统一管 --> com.example:common:${project.version} </dependency>
  </dependencies>
</dependencyManagement>
```

**子模块用法**（以 web 为例，注意没有版本号）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

**父 pom 三个血泪坑**（不继承官方 parent 时必须自己补）：

| 坑 | 症状 | 修复 |
|----|------|------|
| 打包插件没配 repackage | `java -jar` 报"没有主清单属性" | pluginManagement 里显式 `<goal>repackage</goal>`（E00-2） |
| 没开 -parameters | @PathVariable 不写名时报 500 | `<maven.compiler.parameters>true</maven.compiler.parameters>`（E00-3） |
| Lombok 版本跟不上 JDK | IDEA 里 getter/setter"找不到符号" | 显式 dependencyManagement 声明 lombok 1.18.36（**import 的 BOM 不吃属性覆盖**，E08-2） |

## 1.2 分层约定（每个服务都长一个样）

```
XxxApplication.java        启动类（scanBasePackages="com.example" 加载 common 的 Bean）
├── controller/            接口层：接参数(校验) → 调 Service → Result 包装，零 try-catch
├── service/               业务层：业务规则 + @Transactional / @GlobalTransactional
├── repository/            数据层：JpaRepository，方法名即 SQL
├── entity/                实体：POJO+JPA 注解 = 表结构说明书
└── dto/                   出入参：record + 校验注解，与 entity 隔离（防腐层）
```

## 1.3 common 模块的两个核心类（全系统协议）

**统一返回**（所有接口输出同构 JSON）：

```java
// com.example.common.api.Result<T>
Result.ok(data)                          → {"code":0,"message":"success","data":...}
Result.fail(ErrorCode.USER_NOT_FOUND)    → {"code":1001,"message":"用户不存在","data":null}
```

**全局异常**（Controller 零 try-catch 的秘密）：

```java
// com.example.common.api.GlobalExceptionHandler（common 模块，两服务共享）
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)                 // 业务异常 → 精确业务码(1001/1002/1003...)
    @ExceptionHandler(MethodArgumentNotValidException.class)   // @Valid 校验失败 → 400
    @ExceptionHandler(MissingServletRequestParameterException.class) // 缺参数 → 400
    @ExceptionHandler(HttpMessageNotReadableException.class)   // JSON 解析失败 → 400
    @ExceptionHandler(MethodArgumentTypeMismatchException.class) // 类型不匹配 → 400
    @ExceptionHandler(Exception.class)                         // 兜底 → 500（只留给未知异常！）
}
```

> ⚠️ **生效前提**：启动类必须 `@SpringBootApplication(scanBasePackages = "com.example")`，
> 否则扫不到 common 包，异常处理器成摆设。

# 第二部分 · 九大组件逐个接入（每个都有"三件套"）

> 每节固定格式：**解决什么 → ①依赖 → ②配置 → ③核心代码 → 验证 → 坑**。

## 组件 1 · Nacos 注册中心（模块 01）

**解决**：order-service 只知道对方叫 `user-service`，不知道 IP 端口——注册中心就是电话簿。

**① 依赖**
```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

**② 配置**（application.yml）
```yaml
spring:
  application:
    name: user-service          # 注册身份证，全局唯一
  cloud:
    nacos:
      server-addr: localhost:8848
```

**③ 核心代码**：**零**——自动装配完成注册（每 5 秒心跳，停服 15s 不健康/30s 剔除）。
想"看见"电话簿，加一个观察窗接口：

```java
// user-service / DiscoveryController.java
private final DiscoveryClient discoveryClient;   // Spring Cloud 统一发现接口，Nacos 实现

@GetMapping                                      // GET /discovery → 电话簿里有哪些服务
public Result<List<String>> services() { return Result.ok(discoveryClient.getServices()); }

@GetMapping("/{serviceName}")                    // GET /discovery/user-service → 它的实例列表
public Result<List<Map<String, Object>>> instances(@PathVariable String serviceName) {
    return Result.ok(discoveryClient.getInstances(serviceName).stream()
            .map(i -> Map.of("uri", i.getUri().toString(), "port", i.getPort())).toList());
}
```

**验证**：Nacos 控制台 localhost:8848/nacos 服务列表双绿灯；`curl :8082/discovery/user-service`。
**坑**：9848（gRPC）端口必须映射；实例列表有本地缓存+推送，停服后服务名空壳仍在、实例 30s 消失。

## 组件 2 · Nacos Config 配置中心（模块 02）

**解决**：改配置 = 改代码重新打包重启的痛 → 配置托管 Nacos，改完秒级生效。

**① 依赖**：`spring-cloud-starter-alibaba-nacos-config`
**② 配置**
```yaml
spring:
  config:
    import:
      - optional:nacos:user-service.yml   # Data ID=服务名.yml；optional=远端没有也能启动
  cloud:
    nacos:
      server-addr: localhost:8848
```

**③ 核心代码**：动态刷新三要素
```java
@RefreshScope                                   // ① 没有 it：Bean 创建时 @Value 注入一次就定型
@RestController
public class ConfigDemoController {
    @Value("${user.welcome-msg:本地默认值}")     // ② 取不到用冒号后的默认值
    private String welcomeMsg;

    @GetMapping("/welcome")
    public Result<String> welcome() { return Result.ok(welcomeMsg); }
}
```
Nacos 控制台建 `user-service.yml`（YAML 格式）→ 改值发布 → 1~2 秒接口返回新值（**不重启**）。
原理：客户端收到变更 → 发布 RefreshEvent → @RefreshScope 的 Bean 销毁、下次请求时用新值重建。

**验证**：`curl :8081/users/welcome` 改配置前后各一次，值变化。
**坑**：Data ID 拼写（.yml≠.yaml）；核心配置别加 optional（fail-fast 原则）；引导配置（连 Nacos 自己的地址）必须留本地。

## 组件 3 · OpenFeign 服务调用（模块 03）

**解决**：像调本地方法一样调远程 HTTP 接口——声明式，零手写 HTTP。

**① 依赖**：`spring-cloud-starter-openfeign`（⚠️ SC2023 里 loadbalancer 不再传递，**要自己加**，E03-1）
**② 配置**：启动类 `@EnableFeignClients`

**③ 核心代码**（接口 = 契约，无实现类）：
```java
// order-service / client/UserClient.java
@FeignClient(name = "user-service")                       // name = Nacos 里的服务名
public interface UserClient {
    @GetMapping("/users/{id}")
    Result<UserDTO> getById(@PathVariable("id") Long id); // ⚠️ 必须显式写参数名！
}
```
调用方（业务代码毫无 HTTP 痕迹）：
```java
Result<UserDTO> response = userClient.getById(userId);    // 看似本地调用
```

**背后发生了什么（动态代理）**：`@EnableFeignClients` 给接口生成 JDK 代理对象 → 调用被拦截 →
按方法注解拼 HTTP 请求 → 拿服务名查 Nacos → LoadBalancer 挑实例 → 发请求 → JSON 反序列化成 `Result<UserDTO>`。

**验证**：下单 userId=999 → `{"code":1001,"message":"用户不存在"}`（远程判定的）。
**坑**：DTO 字段名必须与对方 JSON 对齐（防腐层：每个服务自己定义影子 DTO，不共享实体类）。

## 组件 4 · LoadBalancer 负载均衡（模块 04）

**解决**：user-service 起多个实例，每次调用发给谁？

**① 依赖**：`spring-cloud-starter-loadbalancer`（Feign/gateway 的 `lb://` 都靠它）
**② 配置**：无（默认 RoundRobin 轮询）
**③ 核心代码**：也无——起第二实例就是它的用法：
```bash
# IDEA 复制 UserApplication 运行配置，程序实参加：
--server.port=8083      # 命令行参数覆盖 yml 的 server.port
```
**验证**：`curl :8082/orders/lb-test`（内部连发 6 次 Feign 调用，记录每次谁接单）→ 端口 8081/8083 交替。
**坑**：停实例后有约 30 秒"脏窗口"（心跳剔除+缓存刷新），生产靠重试兜底。

## 组件 5 · Gateway 服务网关（模块 05）

**解决**：统一入口 + 横切关注点集中地（鉴权/限流/跨域只写一次）。

**① 依赖**：`spring-cloud-starter-gateway` + `nacos-discovery` + `loadbalancer`
（⚠️ **绝不能引 spring-boot-starter-web**——Gateway 是 WebFlux，MVC/WebFlux 水火不容，所以网关不依赖 common）

**② 配置**（路由三件套：id + uri + predicates + filters）
```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service-route
          uri: lb://order-service          # lb:// = 按服务名从 Nacos 挑实例（组件4复用）
          predicates:
            - Path=/api/orders/**          # 断言：什么请求算命中
          filters:
            - StripPrefix=1                # 过滤器：/api/orders?userId=1 → /orders?userId=1
```

**③ 核心代码**：模块 10 后有了验票配置（见组件 10）。业务代码依旧零。

**验证**：`curl :8080/api/orders?userId=1` 与直连 8082 返回完全一致。
**坑**：网关 404 先查断言与 StripPrefix 算没算对；启动失败查 classpath 有没有混进 MVC。

## 组件 6 · Sentinel 熔断限流（模块 06）

**解决**：流量洪峰限流、下游故障熔断、被拒请求给兜底——三件事。

**① 依赖**：`spring-cloud-starter-alibaba-sentinel`
**② 配置**
```yaml
spring:
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8858    # 控制台（懒加载：服务先被请求一次才现形）
```

**③ 核心代码**（注解资源 + 兜底）：
```java
// order-service / OrderController.java
@PostMapping
@SentinelResource(value = "createOrder", fallback = "createOrderFallback")
public Result<Order> create(@Valid @RequestBody OrderCreateRequest request) { ... }

/** 兜底方法三要素：同类、签名=原参数+Throwable、返回类型同原方法 */
public Result<Order> createOrderFallback(OrderCreateRequest request, Throwable t) {
    for (Throwable cur = t; cur != null; cur = cur.getCause()) {   // 沿因果链找业务异常如实上抛
        if (cur instanceof BusinessException be) throw be;         // （Seata 会包一层，直接判不到）
    }
    return Result.fail(429, "下单太火爆啦，请稍后再试");
}
```
规则在控制台配（簇点链路 → createOrder → 流控 → QPS=1）→ 1 秒并发 5 单 → 部分成功部分 429。

**坑**：fallback 签名不对=静默失效；规则存内存重启丢（生产推 Nacos 持久化=组件 2 复用）；兜底收到非预期异常先分清"限流还是基础设施故障"（E08-3/E10-1 教训）。

## 组件 7 · 链路追踪（模块 07）

**解决**：请求穿越 N 个服务，哪一跳慢/错？——每个请求发一张"身份证"（TraceId）全程携带。

**① 依赖**（三个服务都加）
```xml
spring-boot-starter-actuator
io.micrometer:micrometer-tracing-bridge-brave
io.zipkin.reporter2:zipkin-reporter-brave
```
**② 配置**
```yaml
management:
  tracing:
    sampling:
      probability: 1.0        # 全采样（生产 0.1）
  zipkin:
    tracing:
      endpoint: http://localhost:9411/api/v2/spans
```

**③ 核心代码**：**零**——MVC/WebFlux/JDBC 自动埋点。
⚠️ 唯一例外：**Feign 要单独加 `io.github.openfeign:feign-micrometer`**，否则出站调用不产生 Span、
不带追踪 Header → 下游链路"断"成两条（E07-1，学员亲手抓到的 Bug）。

**验证**：下单后 3~5 秒（异步上报）打开 localhost:9411 → Run Query → 瀑布树
gateway → order → user → SQL，每段耗时一目了然。

## 组件 8 · Stream + RocketMQ 消息驱动（模块 08）

**解决**：下单后的后续动作（积分/短信/统计）不阻塞主流程、不互相牵连——异步广播。

**① 依赖**：`spring-cloud-starter-stream-rocketmq`（生产方 order、消费方 user 各加）
**② 配置**
```yaml
# order-service（生产方）
spring.cloud:
  function: —
  stream:
    rocketmq.binder.name-server: localhost:9876
    bindings:
      orderCreated-out-0:            # StreamBridge.send 用的通道名
        destination: order-created-topic

# user-service（消费方）
spring.cloud:
  function:
    definition: orderCreated         # 消费函数 Bean 名
  stream:
    rocketmq.binder.name-server: localhost:9876
    bindings:
      orderCreated-in-0:             # 函数名-in-0
        destination: order-created-topic
        group: user-service-group    # 同组分摊、不同组广播
```

**③ 核心代码**（事件契约放 common，两端共用）：
```java
// 生产：order-service / OrderService.create()
OrderCreatedEvent event = new OrderCreatedEvent(saved.getId(), saved.getOrderNo(), ...);
try {
    boolean sent = streamBridge.send("orderCreated-out-0", event);   // 发后即忘
} catch (Exception e) {
    log.error("事件发送失败。订单已正常创建——MQ 挂了不能拖垮下单");   // 主业务韧性优先
}

// 消费：user-service / OrderEventConsumer.java
@Bean
public Consumer<OrderCreatedEvent> orderCreated() {      // Bean 名 = function.definition
    return event -> log.info("[MQ] 收到订单创建事件：orderNo={}...", event.orderNo());
}
```

**基础设施三件套**（E08-3/3b 血泪）：broker.conf 的 `brokerIP1` 必须=**所有客户端可达的 IP**（不是
host.docker.internal）；**Topic 手动建**（自动建不可靠）：
```bash
docker exec micro-rocketmq-broker sh mqadmin updateTopic -n rocketmq-namesrv:9876 \
    -b 192.168.85.1:10911 -t order-created-topic -r 8 -w 8
```

**验证**：下单 → user-service 控制台 `[MQ] 收到订单创建事件`。

## 组件 9 · Seata AT 分布式事务（模块 09）

**解决**：扣款（user）+ 建订单（order）跨服务两次写，要么都成、要么都滚。

**① 依赖**：`spring-cloud-starter-alibaba-seata`（参与方都加）
**② 配置**
```yaml
seata:
  tx-service-group: default_tx_group
  service:
    vgroup-mapping:
      default_tx_group: default        # key 与 tx-service-group 一字不差
    grouplist:
      default: 127.0.0.1:8091          # TC（seata-server）直连
  data-source-proxy-mode: AT
```
**数据库**：每个参与库都要建 `undo_log` 表（回滚镜像，见 docker/mysql/init/01-init.sql）。

**③ 核心代码**（一个注解 + 两处普通写库）：
```java
// order-service / OrderService.create() —— 全局事务发起方（TM）
@GlobalTransactional(rollbackFor = Exception.class)
public Order create(OrderCreateRequest request) {
    validateUser(request.userId());
    userClient.deductBalance(request.userId(), request.amount());  // 分支①：user 扣款(RM)
    Order saved = orderRepository.save(order);                     // 分支②：订单落库(RM)
    if (request.productName().contains("炸弹")) {                   // 失败注入：验证全局回滚
        throw new BusinessException(ErrorCode.SYSTEM_ERROR, "风控拦截");
    }
    ...
}
```
原理一句话：数据源代理拦截每条写 SQL → 前后镜像写 undo_log → 本地直接提交 →
二阶段全局提交则删镜像 / 回滚则按前镜像生成反向 SQL 补偿。

**验证**：正常单=余额减+订单在；"炸弹"单=**余额自动退回+订单不存在**。
**坑**：undo_log 没建/组名拼写错/XID 传播断（换调用方式时）=回滚一半，比不回滚更可怕。

## 组件 10 · Spring Security + JWT（模块 10）

**解决**：接口上锁——登录换票，网关统一验票，业务服务零安全代码。

**① 依赖**：auth-service 加 `security` + `oauth2-resource-server`（Nimbus 编码器）；
gateway 加 `oauth2-resource-server`（响应式验签）
**② 配置**（两边**同一把密钥**，HS256 要 ≥32 字节）
```yaml
spring.security.oauth2.resourceserver.jwt.secret-key: "micro-learning-secret-key-..."(58字节)
jwt.secret: 同上
jwt.expire-minutes: 120
```

**③ 核心代码**（发证方 + 验票方）：
```java
// auth-service / AuthController.login()——认证 + 签发
authenticationManager.authenticate(                                   // Spring Security 标准认证
        UsernamePasswordAuthenticationToken.unauthenticated(username, password));
JwtClaimsSet claims = JwtClaimsSet.builder()
        .issuer("auth-service").issuedAt(now)
        .expiresAt(now.plus(expireMinutes, ChronoUnit.MINUTES))       // 短时效=泄漏风险小
        .subject(username).claim("userId", userId).build();
Jwt jwt = jwtEncoder.encode(JwtEncoderParameters.from(
        JwsHeader.with(MacAlgorithm.HS256).type("JWT").build(), claims));
```
```java
// gateway-service / SecurityConfig——网关统一验票（响应式）
@Bean
public ReactiveJwtDecoder reactiveJwtDecoder() {          // ⚠️ E10-3：WebFlux 必须手动声明
    return NimbusReactiveJwtDecoder
        .withSecretKey(new SecretKeySpec(secret.getBytes(), "HmacSHA256")).build();
}
@Bean
public SecurityWebFilterChain chain(ServerHttpSecurity http) {
    return http.csrf(disable()).authorizeExchange(ex ->
            ex.pathMatchers("/api/auth/**").permitAll()   // 登录放行
              .anyExchange().authenticated())             // 其余一律验票
        .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults())).build();
}
```

**验证**：无 token → 401；登录拿 token → 带 `Authorization: Bearer <token>` → 200；错密码 → 401。
**坑**：两边密钥不一致=全 401；HS256 密钥 <32 字节=启动失败；Payload 可解码不防读（勿放敏感信息）；签发后无法作废（短时效+HTTPS+黑名单缓解）。

# 第三部分 · 一次"下单"的全链路代码之旅（穿针引线）

> 命令：
> ```bash
> TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" \
>   -d '{"username":"zhangsan","password":"123456"}' | sed 's/.*"token":"\([^"]*\)".*/\1/')
> curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json; charset=utf-8" \
>   --data-binary @/tmp/order.json http://localhost:8080/api/orders
> ```

| 步骤 | 组件 | 发生了什么（代码视角） |
|------|------|----------------------|
| 0 | 组件10 | 登录：AuthenticationManager 验 zhangsan/123456 → NimbusJwtEncoder 签发含 `userId:1` 的 JWT |
| 1 | 组件10 | 网关收到带票请求 → ReactiveJwtDecoder 验签名+exp → 放行 |
| 2 | 组件5 | 断言 `Path=/api/orders/**` 命中 → StripPrefix=1 → `lb://order-service` |
| 3 | 组件4/1 | LoadBalancer 查本地实例缓存（来自 Nacos 推送）→ 挑一个 order-service 实例转发 |
| 4 | 组件10→6 | order-service 的 `OrderController.create`：@Valid 校验 → **@SentinelResource** 检查流控规则 → 放行 |
| 5 | 组件9 | **@GlobalTransactional**：TM 向 TC 申请 XID，全局事务开始 |
| 6 | 组件3/9 | `userClient.deductBalance()`：Feign 代理查 Nacos 拿 user 实例、**请求头带 XID** → user-service 的 `AccountService.deduct` 扣款；数据源代理写 **undo_log** 镜像 → 本地提交 → 注册分支① |
| 7 | 组件9 | `orderRepository.save()` 插入 t_order → 写 undo_log → 本地提交 → 注册分支② |
| 8 | 组件9 | 商品名含"炸弹"？→ 抛异常 → TM 通知 TC → 双分支按镜像补偿（**余额退回+订单删除**） |
| 9 | 组件8 | 成功路径：StreamBridge.send → RocketMQ `order-created-topic` → user-service 的 Consumer 收到（异步） |
| 10 | 组件7 | 全程每跳被自动埋点 → Zipkin 瀑布树：gateway→order→(Feign)→user→SQL |
| 11 | 组件1/2 | 整条链路的实例寻址来自 Nacos 注册表；配置（如欢迎语）来自配置中心 |

**这张表就是本仓库的灵魂**：10 个组件不是 10 个孤立知识点，而是同一条请求的 10 个侧面。
