## 1. 源码与八股深度剖析

### 1.1 为什么超时重试会导致线上资损（标准事故模型）

```
客户端                      网络                     服务端
  │ ── 扣款请求 ──────────────►│ ──────────────────────►│ 扣款成功，已落库
  │ ◄──× 响应丢失/读超时 ──────│                          │
  │ 判定失败 → 重试            │ ──────────────────────►│ 又扣一次！
```

关键认知：**超时 ≠ 失败**。三类网络异常的重试安全性完全不同：

| 异常 | 阶段 | 请求是否已达 | 重试安全性 |
|------|------|-------------|-----------|
| ConnectTimeout | TCP 握手 | ❌ 确定未达（连接都没建立） | 基本安全 |
| ReadTimeout | 等响应 | ✅ 已达，处理结果未知 | **危险**——必须幂等兜底 |
| 503 Service Unavailable | 网关/LB 层 | 未知（可能已进入内部队列） | 未知，按危险处理 |

结论（面试金句）：**重试是网络层的止痛药，幂等是业务层的保险栓；只配重试不配幂等 = 自动化资损**。

### 1.2 三种生产级幂等方案对比与取舍

| 方案 | 原理 | 优点 | 缺点/前提 | 适用 |
|------|------|------|-----------|------|
| ① Redis + Token 令牌 | 进页面先领 token（`SETNX`，含过期）；提交时 `Lua 脚本`原子"验证+删除"token，删成功才执行业务 | 性能极高；天然防重放 | 需要前端配合先领后交；Redis 与业务库非同一事务域（token 删了业务失败要允许重新领） | 高并发写入口（下单/支付按钮） |
| ② 数据库唯一索引防重表 | 业务键（orderId/requestId）插防重表，唯一索引冲突=重复请求 | **最强兜底**，不依赖额外组件；与业务同事务 | DB 写放大；冲突后要区分"处理中/已成功"返回 | 资金/库存等核心链路的**最后防线** |
| ③ 状态机 CAS 乐观锁 | `UPDATE t SET status='PAYING' WHERE id=? AND status='INIT'`，affected=1 才是首撞 | 无需额外表；与业务状态天然一致 | 只适用于**单实体状态流转**场景；并发竞争失败方需友好重试 | 订单状态推进、审批流 |

生产实践 = **组合拳**：入口层 Token（挡 99% 流量）→ 业务层状态机（保证流程单向）→ 防重表唯一索引（兜底资损）。
Redis 侧细节：验证+删除必须 **Lua 原子**（先 GET 后 DEL 两步会把"并发同 token"漏过去）；
防重表细节：冲突后 `SELECT status` 决定返回"处理中"还是"已成功"，不能一律报错。

### 1.3 与重试的联动（本关的架构观）

- Feign 层：`Retryer.NEVER_RETRY`（默认）不动，重试交由**上层业务显式决策**
- 上层重试规则：仅对**可重试异常**（ConnectTimeout、503）重试；ReadTimeout 一律不盲重，走"查询对账/幂等键重放"
- 我们的异常体系（common）：`RetryableException（可重试网络异常）` vs `BusinessException（不可重试业务异常）` 的区分在 Stage 3 会接入全局异常处理器

## 3. 改造实验（Predict → Run → Verify）

1. **资损复现实验**：先不做幂等，用 `for i in $(seq 1 20)` 并发 20 个**相同 requestId** 的扣减 → 记录库存扣了几次（预测 vs 实际）。
2. **防重表实验**：开启方案②后重跑实验 1 → 20 个请求 1 成功 19 幂等；再把防重表唯一索引手动删掉重跑 → 看防线塌陷，体会"唯一索引是兜底"。
3. **Token 竞态实验**：方案①先实现"GET 再 DEL"两步版 → 用 20 并发打 → 应该偶尔出现多次成功；换 Lua 原子版 → 归零。亲眼看"非原子检查"的漏洞长什么样。
4. **CAS 冲突实验**：两个不同 requestId 并发扣**最后 1 件库存** → 只有一个成功，另一个拿到库存不足——理解乐观锁的失败语义。

## 4. 本关必考深水区面试题（@面试 2 拷问）

1. **"你们系统的幂等是怎么做的？"——请按"入口层/业务层/兜底层"三层说出你的方案，并回答：为什么不能只用 Redis Token 一层？**
   （考察：是否有纵深防御观；token 与 DB 不在同一事务域的缝隙）
2. **读超时后你会重试吗？请给出你的重试决策树（异常分类 × 幂等状态 × 业务可逆性）。**
   （考察：ConnectTimeout/ReadTimeout 的本质理解 + 工程判断力）
3. **防重表插入冲突后，你怎么区分"第一次请求正在处理中"和"第一次请求已成功"？两种情况分别该返回什么？**
   （考察：幂等不是简单报错，是状态感知）
