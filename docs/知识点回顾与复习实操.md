## 模块 05（Gateway）知识点回顾

- **网关三件套**：Route（id+uri+predicates+filters）/ Predicate 断言（Path、Method、Header…）/ Filter 过滤器（StripPrefix 等，分前置/后置）
- **lb:// 协议** = 目标是服务名，经 LoadBalancer 从 Nacos 实例列表挑一个（模块 01+04 复用）
- **StripPrefix=1** = 转发前剥掉路径第 1 段（`/api/users/1` → `/users/1`）
- **铁律**：Gateway 是 WebFlux，classpath 不能有 spring-boot-starter-web → gateway-service 不能依赖 common（[gateway-service/pom.xml](../gateway-service/pom.xml) 顶部注释）
- **价值**：统一入口；鉴权/限流/跨域等横切逻辑将来只写在这一处（模块 06/10 的地基）
- 关键代码位置：[application.yml 路由](../gateway-service/src/main/resources/application.yml)、[GatewayApplication.java](../gateway-service/src/main/java/com/example/gateway/GatewayApplication.java)

### 复习实操（15 分钟，自己走一遍）

1. `docker ps` 确认 micro-mysql、micro-nacos 在跑；Nacos 控制台确认 user-service、order-service 在线（不在就 IDEA 重启这两个）；
2. IDEA Maven 刷新 → 启动 GatewayApplication → 日志确认 8080（Netty）；
3. 四条对比验证（返回应与直连一致）：
   ```bash
   curl "http://localhost:8080/api/orders?userId=1"
   curl http://localhost:8080/api/users/1
   curl http://localhost:8080/api/users/welcome      # 配置中心 v2 仍生效
   curl http://localhost:8080/api/orders/lb-test     # 负载均衡仍轮询
   ```
4. 故意犯错：`curl http://localhost:8080/users/1`（无 /api）→ 404，说出一句话原因（没命中任何路由断言）；
5. （选做）编辑 gateway yml 把 user 路由的断言临时改成 `Path=/users/**` 并删掉 StripPrefix → 重启网关 → `curl http://localhost:8080/users/1` 通了 → 改回原样。

## 模块 06（Sentinel）知识点回顾

- **资源**：被保护的对象。URL 资源自动生成（如 `/orders`）；`@SentinelResource("createOrder")` 手动命名（[OrderController.java](../order-service/src/main/java/com/example/order/controller/OrderController.java)）
- **流控规则**：QPS（每秒放行数，保入口）/ 并发线程数（同时处理数，保线程）；效果=快速失败/Warm Up/排队等待
- **熔断规则**：慢调用比例 / 异常比例 / 异常数 → 三态循环 闭合→打开→半开
- **兜底**：`fallback = "方法名"`，签名=原参数+末尾 Throwable，须同类；限流/熔断/业务异常都走它
- **两个特性**：控制台懒加载（服务要先被请求一次才现形）；规则存内存（重启丢，生产推 Nacos 持久化=模块02 复用）
- 关键位置：[application.yml 的 sentinel.transport](../order-service/src/main/resources/application.yml)、控制台 localhost:8858（sentinel/sentinel）

### 复习实操（20 分钟，自己走一遍）

1. `docker ps` 确认 micro-sentinel；打不开控制台就 `docker compose -f docker/docker-compose.yml up -d sentinel-dashboard` 等一分钟；
2. Maven 刷新 → 重启 UserApplication、OrderApplication（**配规则前先重启**，避免规则被内存态清空的困惑）；
3. 先请求一次下单触发心跳：`curl -X POST http://localhost:8080/api/orders -H "Content-Type: application/json" --data-binary @/tmp/order.json`；
4. 控制台 → order-service → 簇点链路 → 对 `createOrder` 配流控：QPS、单机阈值 1；
5. 一秒并发 5 单：`for i in 1 2 3 4 5; do curl -s -X POST http://localhost:8080/api/orders -H "Content-Type: application/json" --data-binary @/tmp/order.json & done; sleep 2; echo`
6. 验收标准：**成功与 429 混合出现**。若全成功 → 按序检查：服务重启过吗？规则配在 createOrder 上吗？配完到压测之间服务重启过吗？
7. （选做）给 createOrder 配"异常比例 50%"熔断 → 连发 userId=999 的单 → 观察打开后 10 秒内全走 fallback → 半开试探。

## 模块 07（Zipkin 链路追踪）知识点回顾

- **Trace**=一次请求的全程（唯一 TraceId）；**Span**=其中一段带耗时的区间，父子成树
- **上下文传播**：TraceId/SpanId 随 **HTTP Header**（b3/traceparent）跨服务传递——链路不断的关键
- **埋点分区**：MVC/WebFlux/JDBC 自动埋点；**Feign 需要单独的 `feign-micrometer`**（E07-1 教训）
- 上报是**异步批量**的，请求完等 3~5 秒再查；采样率 `management.tracing.sampling.probability`
- 关键位置：三服务 pom 的 tracing 依赖、[order yml 的 management 块](../order-service/src/main/resources/application.yml)、UI localhost:9411

### 复习实操（15 分钟，自己走一遍）

1. `docker ps` 确认 micro-zipkin；浏览器开 localhost:9411；
2. Maven 刷新 → 重启 **order-service**（带上 E07-1 修复的 feign-micrometer）→ user/gateway 保持运行；
3. 走网关下一单：`curl -X POST http://localhost:8080/api/orders -H "Content-Type: application/json; charset=utf-8" --data-binary @/tmp/order.json`
4. 等 5 秒 → Zipkin Run Query → 这次主 Trace 应有 **6~7 个 Span**（含 Feign 和 SQL），user-service 不再"单飞"——亲手验证 E07-1 修复生效；
5. 点 Dependencies 页：能看到 gateway→order→user 的**服务依赖拓扑图**。

## 🧭 全链路从零复现清单（模块 00 → 05，新电脑/推倒重来时照做）

> 场景：把 `docker compose down -v` 清掉所有容器数据、删掉 IDEA 运行记录后，从零跑通当前系统。

1. **起容器**：Docker Desktop 打开 → 仓库根目录 `docker compose -f docker/docker-compose.yml up -d` → 等 mysql healthy、nacos 日志出现 started successfully（约 1 分钟）；
2. **建库**（数据卷被删过才需要）：服务启动时 JPA 自动建表，无需手工 SQL；
3. **重建配置**（数据卷被删过才需要）：Nacos 控制台（localhost:8848/nacos）→ 配置列表 → 创建 `user-service.yml`（DEFAULT_GROUP，YAML）：
   ```yaml
   user:
     welcome-msg: "你好，我是来自 Nacos 配置中心的消息 v2"
   ```
4. **编译**：仓库根目录 `mvn clean install -DskipTests` → BUILD SUCCESS；
5. **按顺序启动 4 个进程**（IDEA 各点绿色三角）：UserApplication(8081) → OrderApplication(8082) → GatewayApplication(8080)；启动日志各找一行 `register finished`；网关看 Netty started；
6. **全链路冒烟**（按模块顺序）：
   ```bash
   # 模块00：直连业务
   curl http://localhost:8081/users/1                       # 不存在则先 POST /users 建 zhangsan
   # 模块01：注册中心
   curl http://localhost:8082/discovery                     # 两个服务名
   # 模块02：配置中心
   curl http://localhost:8081/users/welcome                 # 欢迎语 v2
   # 模块03：Feign 远程校验
   printf '{"userId":999,"productName":"x","amount":1}' > /tmp/bad.json
   curl -X POST http://localhost:8082/orders -H "Content-Type: application/json" --data-binary @/tmp/bad.json   # → 1001 拦截
   # 模块04：负载均衡（可选，需 8083 第二实例）
   curl http://localhost:8082/orders/lb-test
   # 模块05：统一入口
   curl "http://localhost:8080/api/orders?userId=1"
   ```
7. 全绿 = 系统健康，可以继续下一模块。
