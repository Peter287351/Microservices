# 数据库设计说明（模块 00）

> 本文档回答两个问题：**表是怎么建出来的？为什么这样设计？**
> 下面的建表语句不是手写的，而是 JPA 在服务第一次启动时根据实体类自动生成的真实 DDL。

## 一、查看真实建表语句的命令

```bash
docker exec micro-mysql mysql -uroot -proot123 -e "SHOW CREATE TABLE micro.t_user\G SHOW CREATE TABLE micro.t_order\G"
```

## 二、JPA 生成的真实 DDL

### t_user（用户表，由 user-service 启动时生成）

```sql
CREATE TABLE `t_user` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `created_at` datetime(6) NOT NULL,
  `email` varchar(100) COLLATE utf8mb4_unicode_ci NOT NULL,
  `phone` varchar(20) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `username` varchar(50) COLLATE utf8mb4_unicode_ci NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `UK_jhib4legehrm4yscx9t3lirqi` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
```

### t_order（订单表，由 order-service 启动时生成）

```sql
CREATE TABLE `t_order` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `amount` decimal(10,2) NOT NULL,
  `created_at` datetime(6) NOT NULL,
  `order_no` varchar(32) COLLATE utf8mb4_unicode_ci NOT NULL,
  `product_name` varchar(100) COLLATE utf8mb4_unicode_ci NOT NULL,
  `status` varchar(20) COLLATE utf8mb4_unicode_ci NOT NULL,
  `user_id` bigint NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `UK_fjie9ovlyccw6819bahkq6b59` (`order_no`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
```

## 三、逐条解释设计决策

### 1. 表是怎么"无中生有"的？

实体类（如 [Order.java](../order-service/src/main/java/com/example/order/entity/Order.java)）上的 JPA 注解就是"建表说明书"：
`@Entity` 表示这是一张表，`@Table(name="t_order")` 指定表名，`@Column(nullable=false)` 对应 `NOT NULL`……
配置文件里 `spring.jpa.hibernate.ddl-auto: update` 让 Hibernate 在**启动时**对比实体与表结构，缺表建表、缺列加列。
学习阶段用它省去手写 SQL；**生产环境禁用**（表结构变更必须走 Flyway/migration 脚本，防止自动改表引发事故）。

### 2. 为什么叫 `t_user` / `t_order`，而不是 `user` / `order`？

`ORDER` 是 SQL **保留字**（`ORDER BY` 里的那个 order），直接建表叫 `order` 时，每条 SQL 都要写成
`` `order` `` 带反引号，极易出错；`USER` 在 MySQL 8 里虽不强制保留，但在 Oracle/PostgreSQL 中是系统关键字。
行业惯例：表名加业务前缀（t_ / tb_ / sys_）避开保留字。

### 3. 主键为什么用 `bigint AUTO_INCREMENT`，不用 UUID？

- **InnoDB 的主键就是聚簇索引**，数据按主键物理排序存储。自增 id 顺序追加，写入快、页不分裂；
  UUID 随机无序，插入时频繁挪数据、页分裂，性能差。
- `bigint` 8 字节，比 UUID 的 36 字符小得多，索引更紧凑。
- **对外展示用业务单号 `order_no`，与物理主键分离**：主键暴露给外部会泄露业务量（每天 id 涨多少，竞争对手能猜出你的单量），且单号要可读、可扩展（雪花算法等），所以两者分工。

### 4. 金额为什么是 `decimal(10,2)` 而不是 double/float？

`double` 是二进制浮点数，**无法精确表示 0.1**（就像十进制写不出 1/3）。
`0.1 + 0.2 = 0.30000000000000004` 的经典问题在钱上不可接受。
`decimal` 是十进制精确存储；Java 侧对应 `BigDecimal`。
`(10,2)` = 总共 10 位、其中 2 位小数，最大 99,999,999.99，对学习项目足够。

### 5. `datetime(6)` 是什么精度？

括号里的 6 表示**微秒级精度**（默认 0 是秒级）。Java 的 `LocalDateTime.now()` 自带纳秒，datetime(6) 能存下微秒，排序时不易撞车。

### 6. `utf8mb4_unicode_ci` 字符集

MySQL 的 `utf8` 是**残血版**（最多 3 字节，存不了 emoji 和部分生僻字）；`utf8mb4` 才是完整 UTF-8（4 字节）。
新项目一律用 utf8mb4。`_unicode_ci` 是排序规则：不区分大小写、按 Unicode 标准排序。

### 7. 唯一索引 `UK_xxx`

`username` 和 `order_no` 建了唯一键：数据库层面**兜底防重复**。
代码里的"用户名已存在"检查（UserService）和数据库约束是双保险——并发场景下两个请求同时通过代码检查，最后靠数据库约束拦住第二个。

### 8. `t_order.user_id` 为什么**不建外键**？

这是本模块最重要的取舍：
- 学习阶段两个服务共库，本可以加外键约束；
- 但**真实微服务是"一个服务一个库"**，user 表在另一个数据库实例里，物理上根本无法建外键；
- 所以从第一天就按微服务的规矩来：**关联关系只存 id，数据一致性由应用层保证**（模块 03 用 OpenFeign 校验用户、模块 09 用 Seata 保证事务），为后续模块铺路。

### 9. 两个服务共用一个 `micro` 库，合理吗？

**学习阶段合理，生产不合理。** 模块 00 的重点是搭骨架，先用一个库降低复杂度；
但记住：服务共库时它们只是"分布式部署的单体"。模块 09（Seata）会切到"一服务一库"，真正体验跨库事务。

## 四、常用数据库操作命令

```bash
# 进入容器内 MySQL 命令行
docker exec -it micro-mysql mysql -uroot -proot123

# 常用 SQL
SHOW DATABASES;                -- 看所有库
USE micro;                     -- 切到业务库
SHOW TABLES;                   -- 看表
SELECT * FROM t_user;          -- 看用户数据
SELECT * FROM t_order;         -- 看订单数据
DESC t_order;                  -- 看表结构
```
